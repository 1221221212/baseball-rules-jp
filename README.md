# 公認野球規則 — 年度版データベース＋差分ビューア

年度ごとの規則を構造化して持ち、**年を選んで読む／2年を並べて改正差分を見る**ためのもの。
改正情報・解釈・事例は条文IDに紐づけて `annotations.json` に貯めていく。

## 使う

```
make serve            # → http://localhost:8000/
```

`index.html` はデータを外部ファイルから読み込むので、**`file://` では動かない**（ブラウザのCORS制約）。
上のコマンドでローカルサーバを立てて開く。

- **条文** — 全条文が1ページに繋がっており、スクロールに追従して目次が現在位置を示す。
  検索は `/` キーでフォーカス、`Esc` で解除。`5.06b3E` のようなIDでも、`5.10l-原注` のような
  公式の引用形式でも引ける。相互参照はクリックで飛べる
- **改正差分** — 上部で2年を選んで比較。「改正箇所のみ表示」で絞り込み。
  表示は**並べて**（左右2カラム）と**インライン**（1本の流れに削除と追加を織り込む）から選べ、
  既定は画面幅で自動的に切り替わる。狭い画面では同じ文を2回読むことになる2カラムより
  インラインの方が読みやすいため（GitHub なども狭い画面では split を無効にしている）
- **注釈** — 左下の［＋ 注釈を作成］から追加。**1つの注釈に複数の条文を紐づけられる**
  （改正や解釈は複数条にまたがることが多いため）。対象は条番号や語句で検索して足す。
  ブラウザに保存され、［↓ 書出］で `annotations.json` として書き出せる
- **表示** — 既定はOSの設定に従う。左下のボタンで 自動 → ダーク → ライト と切り替えられ、
  選択はブラウザに保存される

## コンメンタール

`commentary.html` は条文とは独立した解説のページ。条文からも辿れるが、
それ自体が読み物として完結している。

**採番が変わっても紐付きが失われない。** 参照は「2026年の 5.02」のように
*書いた時点の年度とID* で持ち、表示する年度へは差分の対応関係をたどって読み替える。
2025年に定義が1つ増えて以降が繰り下がっても、解説を書き直す必要はない。

```json
{ "id": "c-0003",
  "title": "ストライクの定義とバントのファウル",
  "refs": [{"year": "2024", "id": "y72"}],     ← 2024年版を見て書いた
  "valid": {"from": null, "to": null},          ← 有効期間（省略可）
  "tags": ["用語"], "body": "…" }
```

この参照は 2025・2026年版では自動的に `y73` に解決され、画面には
「2024年は y72」と読み替えの経緯も出る。廃止された条文を指している場合は
「その年度には無い」と示す。

`valid` で「2024年まで有効」のように期間を区切れる。期間外の年度を表示すると
その旨が出るが、記録としては残る。

必要な区間の差分だけ計算するので、年度が増えても全部を読み込むことはない。

## GitHub Pages に置く

**そのまま動く。** サーバー側で動くものは何もなく、検索も差分もブラウザ内で完結する。
GitHub Pages で動かないのは PHP や Rails のようなサーバー側処理であって、
静的ファイルを fetch して JavaScript で処理するのは問題ない。

このフォルダをリポジトリのルートにして push し、Settings → Pages で公開するだけ。

- 取得するパスはすべて相対なので、`user.github.io/リポジトリ名/` のようなサブパス配信でも動く
  （実際にサブパスで動作確認済み）
- `.nojekyll` を置いてあるので Jekyll の処理は走らない
- `build/cache/`（元サイトから取得したHTML/CSS）は `.gitignore` してある。
  新年度の取り込みにしか使わない中間物で、他サイトの複製をそのまま公開しないため
- 公開されるのは約3.2MB（`index.html` 52KB ＋ 年度データ 1年あたり約650KB）

リポジトリ名は ASCII にしておくとURLが読みやすい（日本語でも動くが percent-encoding される）。

### スマホ

対応済み（390×844で確認）。

- 目次は左上の ☰ から引き出す
- 差分は左右2カラムが縦積みになり、**各行に年（2025 / 2026）を表示**する。
  横並びの見出しだけだと縦積みでどちらの年か分からなくなるため
- 表は枠内だけ横スクロールし、ページ自体は横に溢れない

## 中身

```
公認野球規則/
├── index.html            条文ページの骨組み
├── commentary.html       コンメンタール（独立したページ）
├── commentary.json       解説の本体。手で育てる
├── app.css               共通のスタイル
├── app.js                条文ページ
├── commentary.js         コンメンタールのページ
├── diff.js               差分の定義。DOMに触れないのでNodeからも使える
├── refs.js               年度をまたいだ条文参照の解決
├── manifest.json         どの年度のルール本文があるかの索引（生成物）
├── annotations.json      改正メモ・解釈・事例。手で育てる
├── CORRECTIONS.md        元サイトの誤りを手で直した記録
├── years/<年>/
│   ├── text/*.md         ★マスター。人が直接編集してよい
│   └── data/rules.json   ルール本文（生成物）
└── build/
    ├── 1_import.py       元HTML+CSS → text/*.md（新年度の取り込み時のみ）
    ├── corrections.py    元サイトの明確な誤りの補正（1_import.py から自動実行）
    ├── 2_md2data.py      text/*.md → data/rules.json + manifest.json
    ├── check.py          健全性検査（make check）
    ├── diff_check.js     公式改正文書との照合。差分は ../diff.js を使う
    └── official.json     NPB公式改正文書の対応表（検査専用・成果物に含めない）
```

**ビューアが取りに行くのはルール本文と、あなた自身の注釈だけ。**
差分・改正マーカー・検索は、すべてブラウザ側で本文から計算する。
特定の年度ペアにしか作れないような事前生成データは配らない
（作ってしまうと「2000年 vs 2026年」のような組み合わせで破綻するため）。

**マスターは `years/<年>/text/*.md`**。条文を直したいときはここを直して `make all`。

## 作り直す

```
make data             # text/*.md → data/rules.json と manifest.json
make check            # 健全性検査
make add YEAR=2027    # 新年度を取り込む（元サイトから）
make jsonl            # 手元でgrep/jqしたいとき用（配布しない）
make sqlite           # 手元で全文検索したいとき用（1年2.8MB。配布しない）
```

差分は事前計算しない。年度がN個あると組み合わせは N(N-1)/2 通りあり、
100年なら4,950通りになって破綻する。ブラウザ側で計算すれば数msで済む。

元サイトの明確な誤りだけは `build/corrections.py` で直す（取り込みの最後に自動で当たるので、
再取り込みしても失われない）。根拠は `CORRECTIONS.md` に書く。
**それ以外は手で直さず、元サイトの構造から導出する。**

## 階層とID

```
章 chapter  12   1.00〜9.00 ＋ 補則 / 審判員に対する一般指示 / 用語の定義
└ 条 rule   76   5.02
  └ 項 item      274   （a）
    └ 号 clause  354   （1）
      └ 細目 subclause 60  （A）（i）
```

横断して **注記 note**（注／原注／ペナルティ／規則説明／付記／例外／問答／軟式注）と **用語 term** がぶら下がる。
2026年版で1,330ノード。

| 種別 | ID |
|---|---|
| 条 | `5.02` |
| 項 | `5.02a` |
| 号 | `5.06b3` |
| 細目 | `5.06b3E` / `5.02iii` |
| 注記 | `5.06b3E-付記` |
| 用語 | `y40`（INFIELD FLY） |

公式の改正文書は引用の深さが揺れる（`5.10(l)【原注】` / `9.22【注】` / `4.03(e)【注】`）。
そこで各ノードは `cite_ids` に**段階的に浅くした別名**を持ち、どの深さの表記からでも引ける。
曖昧になる別名は自動で捨てられる。

## 注記の係り先

**元サイトから自動で導出する。手で指定しない。** 手がかりは2つある。

### 1. ラベルが係り先を名指ししている場合

元サイトは `【4.03原注】` `【3.02注】` `【9.22注】` のように、ラベルに条項番号を書いて
係り先を示すことがある（19件）。この場合はラベルが指す位置に置く。

**ラベルの文字は元サイトのまま出す。** 係り先（構造）と表記（条文の文字）は別の話で、
係り先を直すために文字を足したり削ったりはしない。

### 2. ラベルに指定がない場合 — 字下げ量から導出

元サイトは `<ul>` のCSSクラスで本文と注記を書き分けており（注記系だけ font-size 90%）、
`padding-left` が係り先の深さを示している。注記は「**自分より浅い直近のブロック**」に係る。
ただしそのブロックが注記の場合は、その注記自身が自分の文脈より深く置かれているときだけ採用する
（同じ深さに並んでいるだけなら係り先にしない）。

```
3.01   本文          3em
       【注1】        7em  → 直近で浅いのは本文 → 3.01 に係る
       ペナルティ      5em  → 直近で浅いのは本文 → 3.01 に係る
       【注2】        7em  → 直近で浅いのはペナルティ(5em>3em) → ペナルティ に係る
       【原注】        5em  → ペナルティは同じ深さなので飛ばす → 3.01 に係る
```

`5.03` はペナルティ(4em)が項(a)(b)(c)(4em)と同じ深さなので、続く【注1】は
ペナルティではなく条に係る。この条件がないと過剰に係ってしまう。

マスターのMarkdownでは、この深さを `> ` の重ねで表す。`> ` なら条・項に、`> >` なら
直前の注記に係る。同じ深さの注記どうしは兄弟になる（【注1】【注2】が入れ子にならない）。

データ側では `attached_to` が構造上の親、`scope_target` が実際に係る対象。
ビューアでは字下げがそのまま係り先を表す。

## 差分の作り方

`index.html` の `computeDiff` がブラウザ側で計算する（1,300ノードで数ms）。

### 検知するもの

| 状態 | 意味 |
|---|---|
| `added` / `removed` | 条文・注記の追加と削除 |
| `changed` | 文言の変更（語単位のインライン差分つき） |
| `renamed` | 本文は一致していて採番だけずれた（【注4】→【注3】など） |
| `reparented` | **係り先の変更**（注・付記などが別の条項に付け替えられた） |

### 対応付けの考え方

条文の同一性は **(ID・親・本文) の3つ**で見分けられる。改正はこのうち1つか2つを変える。
そこで「**2つが保たれている**」ことを手がかりに対応づけ、残りを追加・削除とする。

| 手がかり | 変わったもの | 導かれる差分 |
|---|---|---|
| 親 ＋ 本文 | ID | 採番のずれ |
| ID | 本文 / 親 | 文言変更 / 係り先変更 |
| 親 ＋ 似た本文 | ID ＋ 本文 | 採番のずれ＋文言変更 |
| 本文 | ID ＋ 親 | 係り先変更 |

3つとも変わったものは追加＋削除と区別できない。原理的にそうなる。

親と配下の対応は互いに依存する（親が採番替えされると配下のIDも動く）ので、
「親＋本文」は新しい対応が出なくなるまで繰り返す。

**対応づけができれば、差分はそこから機械的に導ける。** 変化は同時に起こりうるので
代表を1つ選ばず、`changes: ["text","number","parent"]` として全部持つ。

元サイトの編集マーク `《新》` は比較前に落とす。

`build/diff_check.js` が NPB公式の改正文書と突き合わせて拾い漏れ・誤検出を検査する（`make check`）。
**差分の計算には `diff.js` をそのまま使う**ので、実装は1つしかない。
公式文書の対応表（`build/official.json`）はこちらが手で書き写したもので、
対応表のある年度ペアにしか使えないため、**検査専用で成果物には一切含めない**。

### 公式改正文書との照合結果

| | 追加 | 変更 | 採番替え | 係り先 | 削除 | 公式項目の検出 |
|---|---|---|---|---|---|---|
| 2024 → 2025 | 21 | 24 | 35 | 4 | 24 | **19 / 19** |
| 2025 → 2026 | 10 | 40 | 3 | 0 | 3 | **27 / 27** |

いずれも拾い漏れゼロ。`make check` でいつでも再検査できる。

公式に記載がないのに差分に出るものは、調べたうえで理由を `build/official.json` の
`known` に残す（黙って無視しない）。現在1件あり、2.01(a)(b)の新設に伴って
【軟式注】の推定係り先が動いたもので、改正ではなく推定の限界。

## 表記の統一

- 英数字は**半角**、括弧は**全角（）**
- 本文の数字は **1桁＝全角**（`１アウト`）、**2桁以上＝半角**（`10点`、`127フィート`）
- 条番号・参照ID・括弧ラベル・`【注1】` は識別子なので常に半角
- 機種依存の合字（`㌳㌅㍍㌢`）は「フィート／インチ／メートル／センチ」に展開
- 桁合わせのための全角スペースは表（`| … |`）にする。描画時は罫線を付けない

正規化ルールは**年度間で必ず同一**でなければならない。ここがズレると差分が汚れる。
